# FORECAST//LEDGER

Most forecasting demos know the answer before they make the prediction.

Forecast Ledger doesn't.

It seals forecasts before outcomes exist, grades them when reality arrives, and refuses to forecast when
the available history cannot support the evaluation protocol.

**Live status, from the generated ledger:** 1 forecast **SEALED** (EU27 retail volume of sales,
`2026-Q2 → 2026-Q3`, model **Drift**, backtest MASE **0.7169**, point forecast **105.28**), 1 series
**REFUSED** (German road freight, 27 annual observations against a required 40), 0 graded so far (the
sealed forecast's target period hasn't been published yet), ledger integrity **VERIFIED**. Every one of
those numbers is read out of `site/data.json`, which is itself generated from `data/ledger/ledger.jsonl`
and `data/processed/*.json` — nothing above is hand-typed.

## Why

A forecast is a claim about the future made with information from the past. The only way to know if it
was a good claim is to check it against what actually happened — and the only way to know it was made
honestly is to be able to prove nothing from *after* the forecast leaked into making it. This project
builds the smallest system that can make that proof: an eligibility gate that will say no, four
transparent baseline models, a genuine rolling-origin backtest, a cryptographically sealed forecast
contract, and an append-only ledger that grades forecasts without ever touching what was originally
sealed.

Three other repos in this portfolio (`risk-swarm`, `fraud-watch`) already carry a "publish the failure,
don't hide it" ethic. This one applies the same discipline to time. The resume line "forecasting engine
~95% accuracy" had no repository behind it before this one.

## Data

Two Eurostat series, fetched live via the public REST API (no key, no auth), cached to `data/raw/` so a
rebuild needs no network:

| Role | Dataset | Series | Observations |
|---|---|---|---|
| Forecastable | `sts_trtu_q` | EU27 retail trade volume of sales, index 2021=100, seasonally & calendar adjusted | **106**, quarterly, 2000-Q1 → 2026-Q2 |
| Refusal demo | `road_go_ta_tott` | Germany, road freight, total, million tonne-km | **27**, annual, 1999 → 2025 |

Phase 0 of this project was inspecting real data before writing any forecasting code, and it corrected
two assumptions from the original spec:

- `sts_trtu_q` for the EU27 aggregate reports **142 quarters of time-dimension labels**, but the index
  2021=100 series only has **values for 106 of them** (2000-Q1 onward; 1991–1999 is defined but empty for
  this unit). The tidy series correctly reflects 106, not 142.
- The road freight refusal case is **not** the EU27 aggregate — that one only has 18 observations
  (2008–2025) for any unit. Germany specifically has the full 27 annual points (1999–2025) that the
  refusal demo needs, so the refusal series is `geo=DE`.

Both findings are in `data/processed/data_profile.json`, regenerated by `scripts/fetch.py` on every run.

## Eligibility

`src/eligibility/gate.py` checks, in order: known frequency, minimum observation count, contiguous
history, non-degenerate variance. The observation-count threshold is derived, not chosen to make the
freight series fail — see `METHODOLOGY.md` for the full derivation. In short: 2 full seasonal cycles (or
8 observations, whichever is larger) to train, plus 8 independent non-overlapping 4-step test windows to
trust the backtest, for a floor of **40 observations**. The retail series has 106; the freight series has
27. The rule is dataset-agnostic and `tests/test_eligibility.py::test_exactly_enough_history_is_not_falsely_refused`
exists specifically to catch the failure mode of tuning the number to get the desired demo result.

## Backtesting

Genuine rolling-origin evaluation (`src/backtest/rolling.py`): at every valid origin `T`, each model is
given `history[0..T]` only, forecasts `h = 1..4`, and is scored against the real `T+h` observation once
it's sliced out — never before. `tests/test_backtest_leakage.py` and `tests/test_anti_cheating.py`
specifically test that mutating observations after an origin cannot change the forecast made at that
origin.

## Models

Naive, seasonal naive, drift, and Holt (double exponential smoothing) — nothing else. Holt's smoothing
constants are fixed, not tuned per series or per origin (tuning them against a training window would
itself use knowledge of how that window's future unfolded).

## MASE

Implemented and unit-tested in `src/backtest/metrics.py` / `tests/test_mase.py`, including the
zero-denominator case (constant training window): zero error if the actual is also constant, explicitly
flagged and excluded from the aggregate — never silently coerced — if the actual departs from it.

On the retail volume series, real backtest result across 98 rolling origins:

| Model | MASE | MAE |
|---|---|---|
| Naive | 0.852 | 1.252 |
| Seasonal Naive | 1.225 | 1.805 |
| **Drift (selected)** | **0.717** | **1.070** |
| Holt | 1.017 | 1.518 |

Drift wins on real backtest MASE. It is not preferred for being simple or for being sophisticated — it's
what the numbers say. Selection is deterministic; ties break by a fixed priority order
(`src/config.py:MODEL_NAMES`), never by re-inspecting anything about how the future turned out.

## The seal

Every issued forecast becomes a canonicalized, SHA-256-hashed contract
(`src/ledger/contract.py`): sorted keys, no incidental whitespace, so any later change to any field
changes the hash. The seal proves this exact forecast existed in this exact form before the outcome was
known. **It does not prove the forecast is any good** — a wrong forecast is preserved exactly as
faithfully as a right one.

## Ledger

Append-only (`src/ledger/store.py`), physically one JSON object per line in `data/ledger/ledger.jsonl`.
Three event kinds: `SEALED`, `REFUSED`, `GRADED`. A sealed contract is never rewritten — re-sealing
identical content is a no-op, and re-sealing *different* content under the same forecast_id raises an
error rather than silently overwriting history. `src/ledger/verify.py` independently re-checks every
hash, ordering, and duplicate constraint and reports `VERIFIED` / `WARNING` / `INVALID`.

## Grading

When Eurostat publishes the target period, `scripts/grade.py` locates the matching outstanding sealed
forecast, records the actual, signed error, absolute error, and the data vintage it was graded against —
as a new `GRADED` event appended to the ledger. The original `SEALED` contract is never touched; test:
`tests/test_grading.py::test_original_forecast_unchanged_after_grading`.

## Refusal

`road_go_ta_tott.DE.TOTAL.TOTAL.MIO_TKM` — 27 annual observations, refused with reason code
`INSUFFICIENT_HISTORY` against a required 40. No forecast was issued. Producing a number would have been
easier. Defending it would not.

## Reproducibility

```
pip install -r requirements.txt
pytest -q                        # 59 tests, no network required
python scripts/fetch.py          # fetch or reuse cached Eurostat data, write data_profile.json
python scripts/build.py          # eligibility -> backtest -> selection -> seal (idempotent)
python scripts/grade.py          # grade any outstanding forecast whose outcome now exists
python scripts/verify.py         # independent ledger integrity check
python scripts/build_site_data.py
```

## Limitations

- Only four baseline models. No ARIMA, no ML, no confidence intervals — deliberately.
- Only two datasets, one series each. No country-by-country pages.
- Official statistics get revised. This project distinguishes forecast input vintage from outcome
  observation vintage, but does **not** re-grade a forecast if the underlying observation is later
  revised — the originally graded value stands permanently. Full revision tracking would need a durable
  per-period vintage history that Eurostat's own API does not expose cleanly for these series.
- Rolling-origin backtest performance does not guarantee future performance. Drift winning on 98 origins
  of retail volume history says nothing about whether it will win on the next one.
- MASE measures relative forecast error against a naive benchmark. It is not a universal "accuracy," and
  this project never manufactures an "accuracy %" from it.
- A cryptographic seal proves record integrity — that this forecast existed in this form before the
  outcome was known. It does not and cannot prove predictive validity.
- Refusal thresholds are tied to this project's declared evaluation protocol (horizon, minimum
  independent test windows). A different, equally defensible protocol could draw the line elsewhere; see
  `METHODOLOGY.md` for the specific reasoning used here.
- The static site's JavaScript was validated against the real generated `site/data.json` from the
  command line; it has not yet been visually confirmed in a real browser window from this environment
  (the sandbox here could not keep a local preview server reachable). Worth a quick look before
  screenshots go in this README.
